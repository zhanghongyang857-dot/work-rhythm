# Work Rhythm 开发基准 V2

> 生效日期：2026-08-20
> 本文是当前唯一有效的产品与开发执行基准。`docs/archive/` 中的桌面端文档只供追溯，不得据此继续扩展旧原型。

## 1. 产品目标

Work Rhythm 是一个仅在本机运行的 macOS 个人工作节律工具。它的核心不是管理后台，也不是普通计时网页，而是一个可信、轻量、好看的桌面常驻计时器。

用户工作时，应无需打开复杂页面，只看桌面浮窗便可知道：

- 今天累计进行了多少有效学习／工作；
- 距离下次休息还有多久；
- 正在进行什么活动，以及当前是专注、暂停还是休息；
- 到休息时间后可以立刻开始休息、延后或跳过。

用户也可创建长期活动（如“看论文”），并在日后查看每日／每月投入、活动归属和活跃时段。

## 2. 已确定的产品决策

| 决策项 | 结论 |
| --- | --- |
| 最终形态 | macOS 本地应用，不做公共网页产品。浏览器仅可用于视觉或交互草图。 |
| 产品中心 | 桌面双圆环浮窗；主窗口、统计和设置均为辅助。 |
| 数据与隐私 | 本地优先、无登录、无云同步、无遥测、无后台网络请求。 |
| 默认节律 | 有效专注 50 分钟后提醒休息 5 分钟；用户可修改或关闭。 |
| 第一版活动 | 可创建、选择、暂停、继续、结束和切换的长期活动。 |
| 非目标 | 待办、项目协作、日历整合、内容监控、移动端、主题商店和自动更新。 |
| 视觉原则 | 克制、清晰、低干扰；双圆环是视觉中心。优先系统组件，仅对核心双环做小范围定制。 |

## 3. 核心体验与正确口径

### 3.1 桌面浮窗

浮窗必须无标题栏和系统交通灯，支持拖动、隐藏和恢复，常驻于普通桌面空间；对全屏应用和 Stage Manager 的实际表现必须在目标 Mac 上单独验收。

浮窗包含两个并列圆环：

1. **今日累计**：当天所有活动的有效专注时长之和。暂停、休息和睡眠期间不计入。它绝不是当前这一段计时的时长。
2. **距离下次休息**：当前专注周期中还需要完成的有效专注时间。暂停不消耗倒计时；切换活动不重置周期；开始、跳过或结束休息后进入下一周期。

浮窗需有当前活动和状态文字，并提供最常用的直接操作：开始、暂停／继续、结束、切换活动、开始休息、延后 10 分钟、跳过。

### 3.2 时间事实

- 所有记录以开始、暂停、继续、结束等时间戳保存；不得每秒写入数据。
- 应用只在状态变化时持久化；可见浮窗才每秒刷新展示。
- 同一时刻只允许一项活动处于未结束状态。
- Mac 将要睡眠时自动暂停；唤醒后保持暂停，须由用户主动继续，避免睡眠被计为专注。
- 重启后从保存的时间事实恢复；跨午夜时，今日累计必须按本地自然日切分。

## 4. 技术基线

新开发不再扩展现有 Tauri + React + Rust 原型。新应用采用 Apple 原生框架，减少桌面能力的自定义实现和第三方依赖。

| 层 | 技术 | 用途 |
| --- | --- | --- |
| 语言与应用界面 | Swift + SwiftUI | 浮窗内容、主窗口、活动管理、设置和统计。 |
| 浮窗壳 | AppKit `NSPanel` | 无边框、置顶、拖动、显示／隐藏及窗口空间行为。 |
| 菜单栏 | SwiftUI `MenuBarExtra` | 显示浮窗、快速暂停／继续和退出。 |
| 通知 | `UserNotifications` | 本地休息提醒。 |
| 初期持久化 | `Codable` JSON 文件 | 保存活动、计时事件与偏好，便于快速验证。 |
| 后续持久化 | SwiftData（仅在验证需要后） | 历史查询和统计量增大后再引入。 |
| 图标、图表 | SF Symbols + Swift Charts | 使用系统成熟组件。 |
| 测试 | XCTest + 可注入的测试时钟 | 计时口径、状态机与统计测试。 |

浮窗由 `NSPanel` 承担系统窗口职责，SwiftUI 只渲染内容。配置目标为：无边框、`.floating` 层级、背景可拖动、可跨桌面空间，并针对全屏／Stage Manager 做实机验收。不得用网页模拟窗口行为，也不引入不必要的第三方浮窗框架。

双圆环使用 SwiftUI 原生绘制能力封装为一个小组件；这是唯一需要的核心视觉定制，而不是建立自定义 UI 框架。Codex Pet 只能作为后续可关闭的状态动画灵感，不是计时器的实现基础，也不进入 V0。

## 5. 开发与测试方式

开发过程遵循“先演示、再验收、后扩展”。不允许在用户没有测试核心浮窗前，提前制作完整安装包、管理后台或统计页。

### 5.1 当前开发优先级

**当前目标是验证核心功能，不是完成一个看似完整的 App。** 每次开发只交付一个可独立运行和验证的功能切片；它可以没有完整导航、设置页、数据导入、分发包或所有边缘状态，但必须让用户能真实判断该功能是否正确、好用、符合预期。

在用户明确确认“这个功能符合预期”之前：

- 不为完整性补做外围页面、完整菜单、复杂设置、统计大屏或发布流程；
- 不把“可打包”“能安装”当作该阶段的完成标准；
- 不因界面暂时不完整而替代或掩盖核心功能的真实测试；
- 只实现该功能测试所必需的最小支撑代码，同时保持计时口径和数据安全正确。

完整应用的整合、正式数据迁移、签名、DMG 打包和发布检查，只有在核心浮窗、计时、活动与提醒均经用户验收后才进入计划。用户可在任一阶段要求调整、暂停或否决后续范围。

每个阶段必须提供：

1. 简短的验收清单；
2. 可直接运行的本地调试样机，而不是 DMG 或发布版；
3. 状态模拟入口，例如 `+1 分钟`、`+50 分钟`、`模拟提醒`、`模拟睡眠唤醒`；
4. 自动化测试结果；
5. 用户的视觉与手工操作确认。

调试样机与正式数据隔离，避免测试污染真实记录。阶段完成后才创建 Git 提交；未经验收的功能不合并到 `main`。

### 5.2 阶段完成与用户验收交接

“开发完成”不等于“阶段通过”。每个阶段必须依次经历以下三个状态：

1. **开发者自测完成**：运行相关自动测试、启动调试样机，并按该阶段验收项做一次实际操作检查；发现的问题必须先修复，不能直接交给用户发现。
2. **等待用户验收**：开发者明确告知“已准备好验收”，并给出本节规定的测试说明。此时不得开始下一阶段功能。
3. **用户确认或反馈**：用户标记通过、提出调整，或报告问题。只有明确通过后才提交该阶段并进入下一阶段；有反馈时只修复当前阶段范围内的问题。

每次请求用户验收时，开发者必须在对话中提供一份非技术性的测试卡，且至少包含：

| 必填内容 | 要求 |
| --- | --- |
| 本次测试目标 | 说明本阶段只验证什么，以及刻意没有做什么。 |
| 如何打开 | 给出最简单的本地启动方式；不要求安装、打包或命令行操作。 |
| 测试前状态 | 说明是否为测试数据、是否需要重置，以及测试不会影响什么。 |
| 操作步骤 | 按序号列出用户要点击、拖动或观察的动作。 |
| 每步预期结果 | 明确用户应该看到什么，避免由用户猜测正确行为。 |
| 已完成的自测 | 简述已运行的自动测试与实机检查。 |
| 已知限制 | 如实列出本阶段尚未实现或暂不验证的项目。 |
| 反馈方式 | 请用户逐项标记“通过／不通过／需调整”，并说明观察到的问题。 |

测试卡必须与阶段范围匹配。例如 V0 只要求用户验证浮窗外观、拖动、置顶、隐藏和桌面空间行为；不能要求用户等待 50 分钟或测试尚未实现的真实计时。V1 及后续阶段必须提供模拟时间与异常场景入口，使用户在数分钟内完成原本需要长时间等待的验证。

## 6. 阶段与验收门槛

### V0：桌面浮窗样机

只实现一个静态双圆环浮窗与菜单栏入口。

**验收：** 无边框、可拖动、置顶、可隐藏／恢复；视觉尺寸、配色、文字层级和双圆环布局得到用户确认；跨空间、全屏和 Stage Manager 行为完成实机检查。

### V1：计时内核

实现单个活动的开始、暂停、继续、结束，以及真假时间测试。

**验收：** 左环为正确的今日累计；右环为正确的周期倒计时；暂停不计时；模拟时间和真实时间结果一致；重启恢复与睡眠自动暂停通过测试。

### V2：活动与持久化

实现长期活动、切换活动、JSON 保存和恢复。

**验收：** 可在浮窗中选择活动；切换不产生并行计时；重新启动后当天累计、当前状态和活动记录正确。

### V3：休息提醒

实现本地通知、开始休息、延后和跳过。

**验收：** 模拟及真实到点提醒均正确；休息状态与右环正确；通知权限拒绝时应用内仍可用。

### V4：复盘与管理

实现活动管理、历史修正、每日／每月统计、活动归属和活跃时段。

**验收：** 所有统计都可追溯至原始记录；手动修正后统计重算正确；日常高频操作不超过两步。

## 7. 中间文件、构建产物与磁盘管理

### 7.1 分类与版本控制规则

| 类型 | 位置或示例 | 规则 |
| --- | --- | --- |
| 源码与开发依据 | `Sources/`、测试、`docs/`、项目配置、依赖锁定文件 | 必须进入 Git。 |
| 精选验收证据 | 每阶段最多保留少量压缩截图或简短说明 | 放入 `docs/`，随对应功能提交。 |
| 本地调试产物 | `DerivedData/`、`.build/`、`build/`、`*.app`、`*.dSYM` | 可随时重新生成，绝不进入 Git。 |
| 测试原始产物 | 录屏、完整日志、`*.xcresult` | 放入 `artifacts/`，本地保留且不进入 Git；只将最终必要证据整理进文档。 |
| 分发包 | DMG、归档包、签名后的 App | 不进入 Git；只有明确发布时才存入独立发布渠道或人工归档目录。 |
| 用户数据 | 应用数据目录中的 JSON／数据库和备份 | 不在项目目录中生成，也不清理或提交。 |

`.gitignore` 必须始终覆盖上述可再生成产物。新增工具、依赖或构建流程前，应先确定其缓存和输出目录并补充忽略规则。

### 7.2 编译与清理原则

- 每次改动后**不需要**制作安装包，也不需要进行完整发布构建；日常只运行本地调试样机或相关测试。
- 每个验收阶段结束前必须运行对应测试并启动一次调试版，以确认代码能编译和实际交互可用。这会产生构建缓存，但缓存不属于项目内容。
- 增量编译会复用已有缓存，因此不应在每一次小改动后清理；频繁清理只会让下一次测试变慢。
- 在一个阶段验收完成、暂停开发较久或缓存明显膨胀时，先保留已确认的截图／说明，再清理该项目的可再生成构建产物。不得清理应用用户数据或唯一的分发包。
- 不在项目目录中保留多份调试 App、DMG、录屏或完整构建目录；发布包必须先移出构建目录，再进行清理。

### 7.3 上一版空间膨胀的原因

上一版使用 Tauri + Rust。每次运行、测试或检查都会在 `src-tauri/target/debug/` 生成 Rust 依赖、调试符号和增量编译缓存；Tauri 依赖 macOS WebView、SQLite、通知等原生组件，调试产物尤其大。它们累计后曾占用约 5.2GB。

这不是用户数据，也不是单纯因为“完成开发后才编译”。日常开发和测试本身就需要编译；问题在于这些可再生成缓存长期留在项目目录中，且没有明确的归档与清理规则。V2 改用原生 Swift 后仍会有 Xcode 缓存，但它们会被隔离和忽略，不作为项目文件管理。

## 8. 下一步

下一次实现只允许从 V0 开始：创建原生调试样机，先验证无边框、可拖动双圆环浮窗的桌面行为和视觉。V0 只需是可测试的功能样机，不是完整 App；不得在 V0 验收前开始计时逻辑、数据库、提醒或统计功能。
